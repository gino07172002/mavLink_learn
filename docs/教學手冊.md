# 用 C++ 學 MAVLink：教學手冊

閱讀對象：已經接觸 C++、socket、Pub/Sub、WorkQueue、Commander 狀態機，準備把自己的飛控練習接到外部程式的人。你不必先了解全部 PX4，也不必先學 ROS。

本手冊保留初階 Lab 01～04 的學習順序；後續已補 [QGC 接入教學](../labs/lab01_telemetry/docs/QGroundControl接入教學.md) 與 [Lab 05～08 的真正 PX4／PX4-Lite／進階實作](PX4_SITL與後續實作.md)。下列延伸題若已在新章實作，請以新章及最新驗證報告為準。

這份手冊中的程式名稱與行為，對應工作區內可執行的解答。標記「延伸練習」的項目沒有冒充已完成的功能；真正執行過的範圍以 [驗證報告](驗證報告.md) 為準。

## 1. 先建立三層模型

假設地面站想讓模擬無人機解鎖，這個要求至少跨過三層。

```text
你的業務目的：把 armed 從 false 改成 true
       ↓
MAVLink：COMMAND_LONG 的 command=400、param1=1
       ↓
傳輸：把序列化的 bytes 透過 UDP 送到某 IP:port
```

接收端反向處理：UDP 收到 bytes → MAVLink parser 驗證完整封包 → 解碼成命令 → Commander 決定接受或拒絕 → 發 ACK → 後續 HEARTBEAT 回報 armed 狀態。

這個拆法非常實用。若你完全收不到 UDP，先查埠與路由；若 UDP 有 bytes 卻沒有訊息，查 dialect、CRC、parser；若已經有 ACK DENIED，傳輸通常已經通了，接著查飛控狀態與命令條件。

MAVLink 不負責替你建立 TCP 那樣的連線。本教材的 UDP client 透過應用層 HEARTBEAT 判斷對端是否還活著；`Udp` 固定對端 IP 與埠，`Client` 才管理系統身分、遙測與命令。不要把這兩層合成一個「connected」布林值，否則很難定位問題。

### 1.1 與你熟悉的概念對照

| 原本熟悉的概念 | MAVLink / PX4 對應 | 要小心的差異 |
| --- | --- | --- |
| Modbus 功能碼 | MAVLink message ID、command ID | 兩種 ID 分屬不同層 |
| 裝置位址 | system ID / component ID | 還有 IP/port 這一層網路地址 |
| Pub/Sub topic | uORB topic | MAVLink message 是外部線路格式，不等同內部 topic |
| Commander event | vehicle_command | 命令要經過狀態檢查，未必能執行 |
| 定期工作 | MAVLink stream | 每個 stream 可有自己的傳輸頻率 |
| 通訊 watchdog | heartbeat freshness / setpoint freshness | 檢查的訊息與失效策略不同 |

## 2. 從封包看見協定

### 2.1 MAVLink 2 的外殼

| byte offset | 欄位 | 長度 | 本課怎麼使用 |
| --- | --- | --- | --- |
| 0 | magic | 1 | MAVLink 2 為 `0xFD` |
| 1 | payload length | 1 | 決定本包 payload 的實際長度 |
| 2 | incompatibility flags | 1 | 不理解的不相容功能不能假裝能解碼 |
| 3 | compatibility flags | 1 | 與前一欄不同 |
| 4 | sequence | 1 | 同一傳送通道的循環序號 |
| 5 | system ID | 1 | 發送系統 |
| 6 | component ID | 1 | 發送元件 |
| 7～9 | message ID | 3 | 決定 payload 定義 |
| 10 起 | payload | 0～255 | 長度可能因尾端零值截短 |
| payload 後 | checksum | 2 | CRC 完整性檢查 |
| checksum 後 | signature | 可選 13 | 訊息簽章，不是加密 |

未簽章總長度是 `12 + payload_length`，最大 267 bytes；有簽章最大 280 bytes。payload 內的多位元組欄位使用 little-endian。不要直接把 C++ struct 的記憶體 `sendto()` 出去：padding、排列與 wire format 並不保證相同。官方產生碼負責這些細節。參考 [Packet Serialization](https://mavlink.io/en/guide/serialization.html)。

你要會讀這個結構，但不用在本階段自己手刻 parser。解答中的 `encode()` 呼叫 `mavlink_msg_to_send_buffer()`，`Parser::feed()` 呼叫官方 parser。

### 2.2 三種 ID 怎麼分

以本教材為例，client 的 `(sysid, compid)` 是 `(245, 191)`，bridge 是 `(1, 1)`。245 是這個獨立教學 client 的身分，不代表 UDP 埠；若將來把 companion 視為同一載具的元件，system ID 的規劃可能會不同。

`COMMAND_LONG` 的 message ID 是 76，表示「這個 payload 是七個浮點參數的命令容器」。其中 `command=400` 才表示 Arm / Disarm。若 log 只印「收到 76」，你只能知道收到了命令容器，不能知道對端要做什麼。

此外，封包 header 的 sysid/compid 是**發送者**；payload 裡若有 target_system/target_component，則表示**接收者**。不是所有 message 都有 target 欄位。你看見來自 `(1,1)` 的 ACK，還應確認它是不是回給自己、是不是正在等待的命令。

### 2.3 CRC、dialect 與 sequence

CRC 可以發現傳輸損壞；CRC_EXTRA 把訊息定義納入檢查。它們不提供身分認證。`common`、`minimal` 等 dialect 決定雙方理解哪些訊息；若私有定義不一致，有些封包可能直接驗證失敗。

sequence 從 255 回到 0 是正常現象。多系統、多鏈路與重複轉送會讓遺失率估算變複雜，不能把所有收到的 sequence 混在一起相減。本版沒有實作封包遺失率統計；先把身分與通道邊界設計清楚再做。

### 2.4 練習與參考答案

題目：一個 UDP datagram 裡包含兩個 MAVLink frame，`recvfrom()` 一次成功後，應該呼叫幾次 decoder？

答案：先把 datagram 的所有 bytes 餵給 parser；parser 每吐出一個完整且有效的 frame，才依 message ID 呼叫一次 decoder。因此這個例子會解碼兩個訊息。UDP datagram 的邊界不能直接當成 MAVLink frame 的邊界。

題目：收到半包就把 parser 狀態歸零，可不可以？

答案：不可以把這當成通用作法。parser 必須能跨 feed 保留狀態；在 serial stream 更是必要。UDP 若真的遺失 datagram，則不是「等一等就能補齊」；parser 後續仍需重新同步。`protocol_tests` 同時測試分段、合併與 CRC 損壞後恢復。

## 3. C++ 接收端：bytes → message → 資料

### 3.1 先讀懂 socket 的方向

本機兩個程式使用以下配置：

```text
Client bind 0.0.0.0:14550  ← telemetry/ACK ←  Bridge source port 14560
Client source port 14550   → command/SP    →  Bridge bind 0.0.0.0:14560
```

`bind` 表示「我在哪個本機埠收資料」，`sendto` 的目標則是「對方在哪個 IP 與埠收資料」。沒有規定 MAVLink 永遠使用某一個 UDP 埠；這裡只是教材的預設值。若 QGroundControl 已經使用 14550，改用 Labs 文件中的另一組埠。

本版只接受來自指定 IP:port 的 datagram，避免把不同 UDP 發送來源混進同一 parser。這是單對端模型；它不提供網路身分認證，也不能直接取代多機 router。

### 3.2 為什麼使用 RAII 與 select

`NetworkRuntime` 在 Windows 執行 `WSAStartup()`，結束時 `WSACleanup()`。`Udp` 建構時開啟並 bind socket，析構時關閉；禁止複製，避免兩個物件關閉同一個 handle。Linux 分支改用 POSIX socket 與 `close()`。

`receive(20, callback)` 先用 `select()` 等待最多 20 ms。有資料才 `recvfrom()`；沒有資料就回到事件迴圈，讓計時器與週期傳送繼續前進。若直接使用無限等待的 blocking recv，沒有封包時就沒機會檢查 timeout。

### 3.3 parser 的生命週期

核心邏輯可在 `common/include/lab.hpp` 的 `Parser::feed()` 找到：

```cpp
auto result = mavlink_frame_char_buffer(
    &buffer_, &state_, byte, &message, &status);
if (result == MAVLINK_FRAMING_OK) {
    on_message(message);
}
```

這是教學片段，完整變數與迴圈請看原始檔。本版使用顯式 parser buffer，而不是讓不同連線共用 `MAVLINK_COMM_0` 的隱藏接收狀態。這讓「一條輸入流對應一組 parser 狀態」更容易看見。不要把兩個來源交錯餵進同一組 buffer。官方 C 函式庫的使用背景見 [Using C MAVLink Libraries](https://mavlink.io/en/mavgen_c/)。

### 3.4 HEARTBEAT discovery 與 freshness

`Client::poll()` 發送自己的週期 HEARTBEAT，並用第一個符合條件的飛控 HEARTBEAT 記住對端 sysid/compid。它排除自己的 system ID、GCS 類型與 `MAV_AUTOPILOT_INVALID`；這是單飛控練習的 discovery 策略，正式多機產品應讓使用者明確選定對象。

`last_heartbeat` 使用 `steady_clock` 記錄本機收到的時間。不要拿對端開機毫秒數與本機牆上時間直接相減。也不要用「任何訊息收到就延長 heartbeat timeout」，否則另一個元件持續輸出資料，可能掩蓋飛控元件本身已失聯。

本課 discovery timeout 為 3 秒，heartbeat freshness 為 2 秒，都是**本課設定**，不是 MAVLink 規格強制。通常應依 heartbeat 頻率與鏈路品質調整。協定背景見 [Heartbeat/Connection Protocol](https://mavlink.io/en/services/heartbeat.html)。

### 3.5 ATTITUDE 的資料怎麼看

Lab 01 解碼 `ATTITUDE` 後才轉成角度顯示：`degrees = radians × 180 / π`。網路收到的資料保留原始單位；單位轉換放在輸出或應用邊界，避免同一程式裡一部分以 rad、一部分以 degree 運算。

`time_boot_ms` 表示發送端開機時間尺度，不是 UTC。讀到姿態不代表位置估測也有效。Lab 01 結束時要求至少收到一筆 ATTITUDE；它尚未持續監控 ATTITUDE 自己的 freshness，只有 heartbeat timeout。延伸練習：分別加上姿態與位置的逾時狀態，避免把「系統活著」誤認為「控制所需資料新鮮」。

## 4. 命令 client：把可靠性交給狀態機

### 4.1 三個成功層次

1. `sendto()` 成功：作業系統接受這批資料，不表示飛控收到。
2. 收到匹配的 `COMMAND_ACK`：對端回報處理結果。
3. 觀察到 HEARTBEAT armed 位元改變：應用端確認後續狀態符合目的。

Arm / Disarm 使用 `MAV_CMD_COMPONENT_ARM_DISARM`，param1 為 1 / 0；其餘參數在本課為零。Lab 02 不送強制解鎖參數。完整訊息欄位請查 [Common Message Set](https://mavlink.io/en/messages/common.html#MAV_CMD_COMPONENT_ARM_DISARM)。

### 4.2 解答的命令狀態機

```text
Idle
  → Send(command, confirmation=0)
  → WaitAck
      ├─ ACCEPTED → WaitFreshHeartbeat → 成功 / 狀態確認逾時
      ├─ DENIED / FAILED / UNSUPPORTED ... → 失敗
      ├─ IN_PROGRESS → 等待最終結果（不立即重送）
      └─ 沒有 ACK → confirmation 加一、重送，最多共三次
```

本課一般 ACK 等待 600 ms；收到 IN_PROGRESS 後，改用該次發送起算的 5 秒執行期限，期限不會因每次進度回報無限延長。重送三次仍未回覆時，輸出 `COMMAND_TIMEOUT (outcome unknown)`。**結果未知**很重要：可能飛控已經執行成功，只是回覆全部遺失。

命令協定背景見 [Command Protocol](https://mavlink.io/en/services/command.html)。600 ms、5 秒、三次是範例策略；不同命令與鏈路應採不同期限。

### 4.3 如何匹配 ACK

`ack_matches()` 同時檢查發送者 sysid、compid、command ID，以及 ACK 的 target 欄位。target 為零時，容許它作為缺少 extension 欄位的相容情況；有指定目標時，必須匹配本 client。

這還不能解決所有問題。COMMAND_ACK 沒有你任意指定的 transaction UUID，因此本課只容許一筆 outstanding command。重複送出同一 command ID 的不同參數時，舊 ACK 可能被當成新請求的 ACK。正式產品需要序列化操作、控制時序，並以觀察狀態或命令專屬進度補足，不能只靠 command ID 當全域唯一交易編號。

### 4.4 ACK 後為何等「新的」HEARTBEAT

`Client::confirm()` 記下當下的 heartbeat 計數，必須收到更新的一筆，而且狀態符合，才回報成功。這能避免拿命令前的快取狀態立刻宣告完成。它是應用觀察，不是因果證明：若同時有另一個 client 操作，同樣可能影響狀態。

### 4.5 拒絕與重送的實際意義

`DENIED` 不等於「網路壞了」。在真正 PX4 上，解鎖可能因 preflight 檢查而被拒絕。`result_param2` 不保證有人類可讀的完整原因；可能仍需結合 STATUSTEXT、PX4 events 與飛控 log。本版只顯示 result 名稱、數值、progress 與 detail，不含完整 STATUSTEXT 分段重組。

對本課 Commander，重複 Arm 只會把 armed 設為 true，狀態轉換計數不會重複增加，這就是冪等。但拍照或投放等操作可能不是冪等，不能照搬「沒 ACK 就無條件再做一次」的簡化業務邏輯。

## 5. 從 bridge 接到你之前的 PX4-Lite

### 5.1 分開 transport 與 Commander

`lab04_bridge.cpp` 處理 socket、MAVLink 解碼與編碼。`commander.hpp` 處理命令接受條件與狀態，不知道 UDP 埠，也不呼叫 `sendto()`。

```text
COMMAND_LONG
   ↓ 解碼、檢查 target
VehicleCommand { id, params[7] }
   ↓ Commander::command()
結果碼 + 狀態變化
   ├─ 編碼 COMMAND_ACK → client
   └─ 定期讀狀態 → HEARTBEAT → client
```

這裡 `VehicleCommand` 是內部資料型別。換成自己的 Pub/Sub 時，在解碼後 publish command topic，再由 Commander 的工作迴圈訂閱處理；結果 publish ack topic，通訊模組再訂閱結果並封成 MAVLink。不要把 socket 收發塞進 Commander 的狀態轉移函式。

### 5.2 移植時必須補的 metadata

同步版直接回傳結果，不需要保留太多資訊。但改成非同步 topic 後，除了七個參數，還要帶上來源 sysid/compid、目標、命令 ID、接收時間與外部來源旗標，否則 ACK 回來時不知道要送給誰。

若同時支援多鏈路，還需要路由資訊或由系統 ID 查路由。這些是延伸的架構需求，本課 `VehicleCommand` 刻意只保留最小欄位，沒有宣稱能直接替代 PX4 的完整 topic。

### 5.3 回報頻率與資料新鮮度

bridge 每 250 ms 發 HEARTBEAT，每 50 ms 發姿態和本地位置。這是為了讓測試短時間完成而設計的頻率。姿態是隨時間變化的合成正弦訊號；位置是簡單一階跟隨模型：

```text
position += min(1, 3 × dt) × (target - position)
```

只有 armed 且 offboard 時才移動。這個模型能測試符號、資料流與收斂條件，無法驗證飛行穩定性、推力、重力或真正位置控制器。

### 5.4 bridge 的支援邊界

只處理精確 target `(1,1)` 的 Arm / Disarm、切入 Offboard 與指定 mask 的 LOCAL_NED setpoint；其他命令回 `UNSUPPORTED`。它不實作 broadcast、所有座標系、完整 MAVLink microservices、preflight、動力學或真實安全檢查。

練習：將 `Commander::command()` 改成 publish 到你自己的 command topic，而不是同步呼叫。驗收時應能看到「通訊模組收到 → Commander 處理 → ack topic → 外部 client 收到」，每段帶相同命令 ID 與來源身分。後續已找到相鄰 PX4-Lite 原始碼並完成直接重用模組的 Lab 06；原 Topic 類別未封裝成 library 的差異與新 FIFO 邊界，見 [後續教學](PX4_SITL與後續實作.md)。

## 6. Offboard：一條持續有效的控制資料流

### 6.1 NED 的方向

`LOCAL_NED` 的 x 是北、y 是東、z 是下，單位是公尺。因此 `(2, 0, -2)` 是原點以北 2 m、原點上方 2 m。它不是「目前位置前進 2 m」，也不是 body frame；機頭轉向不會把北方一起轉走。

如果你習慣 ENU，位置轉換的基本關係是 `N = y_enu`、`E = x_enu`、`D = -z_enu`。姿態轉換還涉及旋轉慣例，不能只交換三個 Euler 角。先固定一個座標系，完整標記資料，再談轉換。

### 6.2 type_mask 應該由意思推導

本課控制 x/y/z 與 yaw，忽略速度、加速度與 yaw rate：

```cpp
constexpr uint16_t position_mask =
    POSITION_TARGET_TYPEMASK_VX_IGNORE |
    POSITION_TARGET_TYPEMASK_VY_IGNORE |
    POSITION_TARGET_TYPEMASK_VZ_IGNORE |
    POSITION_TARGET_TYPEMASK_AX_IGNORE |
    POSITION_TARGET_TYPEMASK_AY_IGNORE |
    POSITION_TARGET_TYPEMASK_AZ_IGNORE |
    POSITION_TARGET_TYPEMASK_YAW_RATE_IGNORE;
// 十進位 2552，十六進位 0x09F8
```

IGNORE 位元為 1 表示忽略對應欄位。未忽略的 yaw 在本課送 0 rad。把 velocity 填 0 並不等於「不控制 velocity」；控制欄位是否有效由 mask 決定。`FORCE_SET` 也不是一般 ignore bit，不應為了湊數值隨便設置。

### 6.3 預送、切模式、解鎖、觀察

Lab 03 的流程為：先連上教學 bridge，20 Hz 預送 `(0,0,-2)` 超過 1 秒 → 送 DO_SET_MODE → 等新的 HEARTBEAT 確認模式 → Arm 並確認 → 持續送 `(2,0,-2)` → 檢查 LOCAL_POSITION_NED → 停止 setpoint → 確認退出 Offboard → Disarm 並確認。

最容易犯的錯，是在等待 ACK 時完全停止 setpoint。解答讓 `command()` 與 `confirm()` 接受 `service` callback；每次等待迴圈都呼叫它，週期到了就繼續送 setpoint。單執行緒就能做到，不必先引入資料競爭。

本課使用 `next = now + 50ms`，迴圈延遲時不補發一串過期控制資料。正式控制器還應量測實際頻率與 jitter，遇到 stale input 時採明確策略。

### 6.4 HEARTBEAT 不等於控制生命訊號

PX4 Offboard 需要持續的有效控制訊號，文件要求維持大於 2 Hz，並在切入前先提供超過 1 秒。MAVLink 路徑使用支援的 setpoint 訊息提供這項訊號。失聯時間與處置涉及 `COM_OF_LOSS_T`、`COM_OBL_RC_ACT` 等條件。參考 [PX4 v1.17 Offboard Mode](https://docs.px4.io/v1.17/en/flight_modes/offboard)。

教材 bridge 用「setpoint 最後收到時間超過 0.7 秒」模擬離開 Offboard，位置留在最後值，armed 狀態仍保持，之後由 client Disarm。這個 HOLD 只是教學策略，**不是 PX4 實際 failsafe 或降落邏輯**。

Lab 03 刻意讓 client HEARTBEAT 在停止 setpoint 後持續發送，讓你看到「client 還活著」與「控制流仍有效」是兩件事。完整 SITL 練習不能靠這個玩具模型驗收；見下一章。

## 7. 閱讀真正 PX4，再做 SITL 驗收

### 7.1 固定版本與閱讀問題

### 7.2 與本課比對，才知道哪些被省略

本課 Commander 是同步函式，PX4 是模組與 topic 互動；本課直接保存 Euler 合成值，PX4 ATTITUDE stream 會處理實際姿態表示；本課只接受一組 mask，PX4 還處理更多支援條件。你閱讀原始碼時，要逐一寫下「簡化模型做了什麼」與「PX4 多了什麼」，這樣比只記住檔名有效。

### 7.3 SITL 操作與驗收分開記錄

初版 WSL 啟動失敗；後續成功啟動並找到既有 PX4 build，已在不同版本 `6db88017b8` 完成 SIH 實驗，見 [後續章節](PX4_SITL與後續實作.md)。以下仍是 **v1.17.0 待執行流程**，不能把新版本結果套用為這個 tag 已通過。模擬器與工具鏈安裝請依 [PX4 v1.17 Simulation](https://docs.px4.io/v1.17/en/simulation/) 選擇相容平台。

在有完整 PX4 toolchain 的 Linux 環境，可用對應版本的專案建立 SITL，例如：

```bash
git clone --recursive --branch v1.17.0 https://github.com/PX4/PX4-Autopilot.git
cd PX4-Autopilot
# 先依官方平台文件安裝 toolchain、Gazebo 與相依項
make px4_sitl gz_x500
```

PX4 shell 先執行 `mavlink status`，檢查使用中的 instance 與埠。若要獨立測試本 client，可以新增專用 instance，例如同機 Linux：

```text
mavlink start -u 14660 -o 14650 -t 127.0.0.1 -m onboard -r 200000
mavlink stream -u 14660 -s ATTITUDE -r 20
mavlink status
```

這些命令需在實際 v1.17.0 shell 先查 `mavlink help` 核對；本次沒有執行驗證。`-u` 是 PX4 本地埠，`-o` 是遠端埠。兩個都在相同網路命名空間時，Linux client 可以：

```bash
./build-linux/lab01_telemetry 14650 127.0.0.1 14660 10
./build-linux/lab02_command arm 14650 127.0.0.1 14660
./build-linux/lab02_command disarm 14650 127.0.0.1 14660
```

Windows 與 WSL/VM 分處不同網路時，必須查明雙方實際可達 IP；本課固定來源 IP:port 過濾，不能假設 localhost 轉送一定符合。若收不到資料，先用相同 Linux 環境跑 client，減少網路變因。

Lab 03 的現成解答限定教學 bridge，不會直接對 PX4 起飛。移植到 SITL 時，至少要新增位置有效性、模式／arming 狀態、操作範圍、正常降落與結束處理，將刻意中止 setpoint 的失聯實驗獨立出來，並記錄實際 failsafe 參數。只刪掉 generic 檢查不足以完成移植。

| SITL 驗收項目 | 要留的證據 | 本次狀態 |

## 8. 後續延伸：每個 microservice 解決不同問題

以下是後續設計練習，不在本版實作範圍。可從 [MAVLink Microservices](https://mavlink.io/en/services/) 進一步閱讀各官方協定。

### 8.1 Parameters：長期設定的讀寫

先做一個唯讀參數清單 client：收集參數名稱、索引、總數與型別。網路可能丟資料，所以「收到一筆」與「列表完整」應是不同狀態。完成後再做寫入與回讀核對，記錄修改前值以方便復原。不要把參數寫入當成高速控制迴圈。

### 8.2 Mission：有限序列的交易

航點上傳需要管理序號、對端索取項目、逾時與最後完成回覆。與持續傳送最新目標的 Offboard 不同，Mission 有一份要保持一致的完整資料集合。延伸練習可以先用假對端要求重傳某一項，檢查你的 client 是否仍能完成交易。

### 8.3 Routing：多機、多元件、多鏈路

一台載具可能有飛控、相機、companion；同一個系統還可能經過多條鏈路。設計時先列出 system/component 的唯一性，再決定哪些資料需要轉送，避免回圈、錯送與把不同載具的狀態混在同一份 cache。現在的 `Client` 只鎖定第一個飛控，不具有這些功能。

### 8.4 Signing 與時間

訊息簽章可用來驗證來源與檢查重播相關資訊，但不會把 payload 變成密文。正式產品還需要管理金鑰、時間、鏈路政策與未簽章資料的處理。本課封包沒有簽章，不該因為 CRC 正確就說對端可信。

Time synchronization 則要先分清楚 monotonic time、boot time 與 UTC。延伸練習：先畫出你要比較的兩個時間戳來自哪個 clock，再決定要不要同步、如何補償延遲。

### 8.5 何時使用 MAVSDK

當你已經能解釋 transport、discovery、ACK、freshness 與控制流，便可用 [MAVSDK 文件](https://mavsdk.mavlink.io/main/en/) 比較高階 API 如何包裝它們。底層實作練習用來建立判斷能力；產品是否使用 SDK，取決於支援功能、平台與維護成本，不必把自己維護所有 microservices 當成必經之路。

## 9. 常見問題：依證據縮小範圍

| 現象 | 先查哪裡 | 下一個實驗 |
| --- | --- | --- |
| bind 失敗 | 本機埠是否已被另一程式占用 | 換兩個獨立的測試埠 |
| discovery timeout | bridge 是否在跑、IP/port 是否配對 | 對照 BRIDGE_READY，先跑本機 loopback |
| 有 UDP 沒有 message | 來源過濾、dialect、CRC | 加 bytes 計數與 bad_frames 統計 |
| 有 HEARTBEAT 沒 ATTITUDE | 對端是否有開 stream | 檢查 stream 設定，別一直換 parser |
| ACK DENIED | 命令條件或 preflight | 看 result、事件與飛控 log |
| COMMAND_TIMEOUT | 路徑、目標、ACK 匹配與回傳路徑 | 看 bridge 是否印 VEHICLE_COMMAND |
| ACK ACCEPTED 但程式失敗 | 沒等到新的目標狀態 | 跑 no-state 情境理解這個差別 |
| Offboard 切不進 | 預送持續時間、頻率、位置有效性 | 先固定 frame/mask，避免同時改很多量 |
| 等 ACK 時掉 Offboard | 等待程式是否阻塞控制流 | 量測 setpoint 發送間隔 |
| 往下飛而非往上 | NED z 符號 | 在模擬端先用 z=-2 驗證 |

讀完後的最低完成標準：你能從 log 指出一筆命令的來源、目標、command ID、ACK 結果與後續狀態，也能解釋斷線時哪些結果是「失敗」、哪些只是「未知」。
